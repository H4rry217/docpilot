# DocPilot Filesystem

DocPilot Filesystem 是 DocPilot 的路径优先访问层。它让服务和 agent 可以用同一种方式处理文档和外部存储：路径、目录、文件、搜索和检索。

## 为什么需要它

DocPilot 的内容不只存在一个地方。有些内容来自工作区文档，有些可能来自本地存储，也有些来自 S3 兼容对象存储。上层功能在列目录、读文件、搜索或语义检索时，不应该每次都关心底层到底是哪一种存储。

DocPilot Filesystem 给系统提供了一个统一边界。调用方只需要面对路径，文件系统层负责判断这个路径属于哪个挂载来源。

## 核心概念

### 路径优先

最核心的想法很简单：内容通过路径访问。一个路径可以指向工作区里的文件夹节点、文档快照、本地文件，也可以指向远端 provider 中的对象。

这个边界对用户功能和 AI 工具都很有用。两者都可以把内容理解成一棵树，而不是学习每一种底层存储的细节。

### Mount

组合文件系统可以把多个子文件系统挂到同一棵虚拟树上。例如一个分支代表工作区文档，另一个分支代表 provider 后面的存储。

路径解析采用最具体的前缀。也就是说，更深的挂载可以覆盖更宽泛的父路径，同时整棵树仍然可以被正常浏览。

### Capability

每个挂载都有明确的能力集合。某个子文件系统本身也许可以写入或删除，但挂载时可以只暴露只读能力。

当前只读挂载包含列目录、读取、查看状态、文本搜索、语义检索和读取 URL。写入、删除、复制和移动都需要显式开放。

这样权限控制会贴近路径进入组合树的边界。

### Provider 和工作区内容

Provider 用来暴露具体存储系统，例如本地文件系统或 S3 兼容对象存储。

工作区内容不太一样：它来自 DocPilot 的工作区节点和文档快照。Workspace Filesystem 会把这些节点呈现成目录和文件，但数据来源仍然是工作区相关的 repository。

最终效果是：不同来源的内容可以共享同一套路径模型。

### Search 和 Retrieval

文件系统层支持两种找内容的方式：

- 文本搜索，用来查找文件里的字面量匹配
- 语义检索，用来根据问题找相关片段

工作区语义检索会在配置后使用知识检索服务。文件系统层仍然负责路径范围控制，所以检索结果会被映射回调用方能看到的路径，并限制在请求的子树内。

### Read URL

有些挂载来源可以提供直接读取内容的 URL。这是可选能力。调用方不应该假设每个路径都有 read URL。

## 它在项目里的位置

DocPilot Filesystem 位于工作区功能和 agent 工具的下方。它提供统一的列目录、读取、查看状态、搜索和检索方式，让上层不必到处写 provider 相关逻辑。

它不替代工作区数据库、知识索引或认证系统。那些系统仍然负责各自的事实来源。文件系统层只是把这些能力整理成路径形式的访问面。

## 当前职责

DocPilot Filesystem 当前覆盖：

- 虚拟路径和路径规范化
- 组合挂载
- 挂载边界上的能力控制
- 本地 provider 和 S3 兼容 provider
- 通过文件系统视角访问工作区文档
- 列目录、读取、状态查看、glob、文本搜索、语义检索和可选 read URL

它不负责：

- 判断工作区属于谁
- 存储工作区元数据
- 构建知识索引
- 保证每个挂载都可以写
- 用不相关的行为掩盖 provider 失败

## 工作模型

可以把 DocPilot Filesystem 理解成一张地图：

- path 是地址
- mount 决定地址属于哪个来源
- capability 决定调用方在那里能做什么
- provider 和 workspace filesystem 负责拿到真实内容
- search 和 retrieval 让内容可以被发现

后续扩展这个模块时，最重要的是保持这套模型清晰。
